# 公众号发现与含评论归档：GitHub 方案调研

调研日期：2026-10-17（北京时间）；本轮只检索公开文档、发布记录、作者公告和源码，不安装或执行候选工具，不请求真实微信接口、不登录或抓取凭证。记录中的「作者报告」和「源码证据」均不是留墨实测通过。脱敏版本与证据索引见 [研究索引](/Users/chenge/project/liumo/evidence/feasibility/github-solutions.json) 。

后续同日已按用户指令完成 [exporter 机制研究](/Users/chenge/project/liumo/docs/exporter-mechanism.md) ：主下载器、评论后端、回复补取及 PDF 链路现已取得源码，补充本文首轮未读到的部分；不能再将简化 getComment 视为实际完整下载链。真实接口与截图可用性仍未通过。

## 结论与问题拆分

微信读书是发现第三方公众号文章的候选入口，不是读取公众号正文的必需依赖。需要分别判断文章发现、正文与图片下载、评论与回复获取、原页截图四项能力；某项可用不能代替其余验收。

HTTP 获取正文有现成实现经验；评论也有凭证接口实现。现有证据不支持「只改成微信 User-Agent 就能获得完整留言与回复」：exporter 明确要求微信会话中的参数，而不只是请求头。接口拿到数据后重新排版或导出 PDF，也不能直接当作原始微信页面的完整单张截图。本轮未找到全部满足留墨要求的即用开源组合，不能据此断言不存在其他方案。

### exporter：评论接口存在，凭证获取成本不可忽略

[项目公告 #200](https://github.com/wechat-article/wechat-article-exporter/issues/200) 中，维护者于 2026-07-30 宣布停止维护，归因于核心上游接口关闭，并说明 Credential 备用通道不能作为完整替代。这是作者对其项目的当前结论，不是本项目实测，也不证明所有公众号后台接口都已关闭。当前不把旧教程的一键同步能力当作可用事实。

已读取版本：`package.json` 为 `2.3.21`，固定提交 `152f23832c7f3664b86148e84bd3f75e513e4dd2`。[接口源码](https://github.com/wechat-article/wechat-article-exporter/blob/152f23832c7f3664b86148e84bd3f75e513e4dd2/apis/index.ts) 的 `getComment` 要求 `__biz`、`uin`、`key`、`pass_ticket`，从浏览器 localStorage 读取后交给部署站点的 `/api/web/misc/comment`；`getArticleListWithCredential` 则保留 `begin` 分页。所读前端函数未证明完整评论／回复分页；后端和截图链路尚未完整核对。

[作者凭证教程](https://docs.mptext.top/advanced/wxdown-service) 要求在微信内打开目标号文章，经本机代理提取凭证并同步至网站。每个公众号的凭证不同；教程给出的约 25 分钟有效期是作者描述，未在留墨验证。Mac 路径需要从 Python 源码运行，并安装受信任 CA、修改系统代理；当前授权边界禁止这些系统改动，本轮未实施。使用在线站点会把凭证交给其部署端；即使自行部署，也必须先核对代理范围、存储和请求去向，不能直接使用公共服务。

因此，该方案能回答「评论能否走接口」：已有实现可研究；不能回答「只换请求头即可」「长期无人干预可用」或现有评论业务码 `-3` 的具体原因。MIT 代码许可不等于微信接口授权或持续可用承诺。

### wx-kit：近期仍发布，但最新一篇是明确产品边界

[README](https://github.com/monkeychen/wx-kit) 和已读取的 `v0.12.2` Roadmap 明确说明列表受服务端按账号限制，现有订阅只能取得最新一篇；更换请求栈的尝试是作者自己的调研记录，不是留墨验证。[v0.12.2 发布记录](https://github.com/monkeychen/wx-kit/releases/tag/v0.12.2) 显示发布于 2026-10-08，对应提交 `bb2bcfb319c9875b0f9d9fa4f8966b6e2b060ffc`；访问时 main 为 `b6a32ee5ed56a89c7c5c4fd25dab966619930982`。

[作者开发记录](https://github.com/monkeychen/wx-kit/blob/main/docs/devlog/wx-kit-vibe-coding.md) 描述了普通正文先 fetch、遇新模板空壳再用 offscreen BrowserWindow 渲染的流程。它支持把可见窗口与下载过程分离，但仍可能需要 Chromium；CLI 不等于完全没有浏览器内核。正文实现的固定版本文件本轮未成功读取，不将开发记录升级为完整源码审计。

文档提供微信读书扫码入口；具体会话落盘、Cookie 保护和全部请求去向尚未完成源码核对，不能用其 AI Key 的加密描述替代微信凭证结论。项目为 Apache-2.0；代码许可、维护活跃和 Mac 支持均不能补足多篇覆盖缺口，依赖接口也没有官方稳定性保证。

### WeRSS：分页源码与现实限制之间仍缺证据

固定提交 `9b40351fd1913e7f74cf88f65740cd67a28baf81` 的 [采集代码](https://github.com/rachelos/we-mp-rss/blob/9b40351fd1913e7f74cf88f65740cd67a28baf81/core/wx/model/weread_mp.py) 使用 `/web/mp/articles`、`bookId`、`offset` 并解析多篇，同时存在最新封面回退。与 wx-kit 的当前限制说明存在需要解释的差异：本轮没有相同账号、相同时间、相同公众号的真实请求，不推测哪一方普遍正确。

本项目此前已经核对其凭证、书架枚举／加入、多账号切换、关闭 TLS 校验和 token 输出等边界，详见 [可行性报告](/Users/chenge/project/liumo/docs/feasibility.md) 。留墨仅借鉴最小只读请求，不整体采用，也不采用最新一篇降级冒充完整追更。两目标号的识别、覆盖、真实时间和分页仍未通过；自托管成本、接口权限及持续维护均不因开源或近期提交而自动解决。

## 建议与剩余证据

1. 调整原建议：暂不把继续扫码、找公开标识或更换请求头作为下一项必做操作。用户已完成微信读书扫码，无需重做；先解决候选来源对多篇覆盖的证据冲突。
2. 正文层可借鉴 HTTP 获取与离线图片处理；评论层定点参考 exporter。后续只读代码核对应补齐评论后端、回复分页、凭证续期和去向，不先安装整套服务。
3. 截图单独保留验收：可见 Chrome 窗口未必是最终运行方式，但真实原页需要可正常加载评论的渲染路径。接口数据重建页面、改用 PDF 或拆图都属于待用户决定的替代选项，本轮未采用。
4. 若后续确认开源发现来源都不能多篇补抓，应拿出对应证据，再比较其他合规来源或明确需求取舍；不暗中提高检查频率、缩减为最新一篇，也不把第三方服务接入视为已授权。

本轮三组候选均未证明可识别并完整覆盖猫笔刀和 stormzhang；没有新增自动发现、评论截图或设备实测通过项。Goal 保持未完成；当前不要求用户登录、安装或执行新命令。
