## 我们此前路线的问题

1. **验证顺序错误。** 自动发现是核心产品前提，尚未建立两个号的可靠列表，就将大量工作投入评论凭证、TLS、页面脚本。应先拿到可覆盖多篇的来源，再做最小归档闭环。
2. **缺少及时止损。** 多次刷新只取得计数或未命中目标响应后，仍不断增加专项模式，系统收尾与安全回归逐渐代替产品验收。我没有及时压缩研究范围，造成用户反复配合。
3. **一次现场证据不能支持下一次分析。** 授权下只留聚合计数、丢弃 HTML，后续每缺一个字段便再次申请现场实验；又直到 C28 才发现本地 AST 容量上限。早期应该先确定最小证据需求与资源预算，无法取得时及时换路线，而不是把诊断链越搭越长。
4. **源码差异没有成为早期验收关口。** 当前已经正确展开 `subReviews`；问题不是漏遍历，而是标识／链接格式与分页语义仍缺目标样本验证。测试数量不能弥补这一缺口。

已有工作可复用：正文转换和本地配图、独立身份核对、未完成任务队列、不可覆盖归档、重叠锁和上海时区门控。C20 已取得猫笔刀正文 HTTP／身份分项通过；旧两篇 Markdown／截图是部分成功。C28 的失败是本地节点上限，不能写成微信拒绝或评论根因。保留全部旧文件和证据，不将它们追溯改成 V1 整体验收通过。

## 采纳后的路线与剩余依赖

先以项目隔离的微信读书会话，验证两个指定号的身份、多篇、跨页、原链接及时间；通过后自行实现最小来源读取与 `/web/mp/content` 候选接入，复用现有成熟归档组件。匿名公众号原链接作为正文候选路径，按同文身份与权限验收，不用微信 UA 冒充会话。

发现与归档仍然分离，但不建设通用插件层。来源侧标识与公众号／文章身份建立别名关系，正文哈希用于变化检测，不能凭同一纯文本哈希合并不同发布。状态可使用标准库 SQLite 事务，文件仍是内容主存储；不引入 iCloud 同步状态、不增加大模型或 Docker 产品栈。

若列表只返回最新一篇、覆盖不能证明，或者反复访问受限，关口失败即停止来源实现，提交已知缺口与最多一个备选来源的具体评估。合集只作有覆盖证据时的补充；不自动购买 Wechat2RSS，不因 API 返回错误就要求用户反复扫码。若原页整图仍不可靠，提交一个可对照样本，由用户决定是否接受重排长图或 PDF；本次没有取得该变更授权。
